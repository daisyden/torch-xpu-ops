## Root Cause

test_conv_large_xpu compares Conv2d backward weight gradients in one full backward pass vs chunked
passes; on XPU fp16 they diverge. Consistent with oneDNN selecting different reduction trees/work
partitioning for different batch sizes, so fp16 non-associativity amplifies accumulation-order
differences. Backward-weight accuracy issue (not a crash); already reflected by the XPU skip tied to
#3975.

## Fix Approach

- In XPU Conv2d backward-weight, force a numerically stable fp16 path invariant to chunking: accumulate in fp32 with a fixed reduction order, or route affected shapes to a deterministic/reference GEMM-based kernel instead of the oneDNN variant that changes reduction topology by batch split.
- Add a regression checking full-vs-chunked backward-weight closeness.
- remove/relax the skip once parity is verified.
