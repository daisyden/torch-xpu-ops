## Root Cause

Triggered in c10d default process-group setup: the PG name is 'gloo' but its default backend type
resolves to GLOO (type 1) without a registered backend instance, so rank/size access fails in
ProcessGroup::getDefaultBackend. In XPU test paths, backend selection/registration is split between
GLOO (CPU) and XCCL (XPU), and test_c10d_common still exercises gloo init in a way that leaves the
default PG backend map inconsistent. A backend dispatch/registration issue in core distributed init,
not a kernel issue.

## Fix Approach

- In upstream c10d init, enforce that any selected default backend is registered before _update_default_pg (or fail early with a clear 'backend unavailable for device' error rather than a late default-backend lookup failure).
- For XPU distributed tests, use explicit backend strings matching device reality ('xccl' for XPU-only, or 'cpu:gloo,xpu:xccl' when CPU collectives are needed) and gate/skip pure-gloo paths on XPU configs.
- Add a regression asserting no missing-default-backend state after init_process_group on XPU builds.
