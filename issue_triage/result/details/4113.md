## Root Cause

oneDNN 3.13 behavior change for f16 grouped/depthwise conv on XPU: accumulation-mode selection no
longer lands on the fastest path by default, so kernels use a slower accumulation strategy and E2E
latency increases ~1.3x-2.1x on PVC/Xe2. A dependency-driven perf regression (>7%), not a
model-level workload change.

## Fix Approach

- In the XPU convolution integration path, explicitly set oneDNN accumulation_mode::any for the affected f16 grouped/depthwise conv primitives so the implementation chooses the fastest valid accumulation path.
- Scope to impacted configs (grouped/depthwise + f16).
- validate with targeted microbenchmarks and E2E perf checks on PVC against oneDNN 3.13 to confirm recovery.
