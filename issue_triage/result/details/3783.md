## Root Cause

aten::clone is implemented generically by allocating an output and unconditionally copying the
source at aten/src/ATen/native/TensorFactories.cpp:2270-2292, so XPU clone performance is dominated
by the XPU copy_ backend. The XPU copy path uses memcpyAsync only for same-dtype contiguous copies
in third_party/torch-xpu-ops/src/ATen/native/xpu/Copy.cpp:58-69 and otherwise creates contiguous
temporaries, converts/expands the source, recursively copies, and may copy back to the destination
at third_party/torch-xpu-ops/src/ATen/native/xpu/Copy.cpp:184-235. The OOB data shows a quantified
+0.0097 geomean R delta on B580 (>0.7%) across 18 models, consistent with unnecessary memory-format
conversion and extra device copies in Copy.cpp for clone-heavy vision models.

## Fix Approach

- Collect clone call sites and tensor strides/memory_format for the worst models, then optimize Copy.cpp to avoid temporaries for non-overlapping dense preserve-format clones and add direct strided device-copy kernels where safe.
- Add focused clone/copy microbenchmarks for contiguous, channels-last, and common detectron2/timm strides on B580/G31 and validate that semantic clone behavior and autograd aliasing remain unchanged.
