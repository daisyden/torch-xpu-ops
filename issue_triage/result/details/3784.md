## Root Cause

native_batch_norm is registered as an XPU override in
third_party/torch-xpu-ops/yaml/native/native_functions.yaml:4926-4932 and implemented by
batch_norm_xpu, which allocates output/save tensors then calls xpu::batch_norm_kernel at
third_party/torch-xpu-ops/src/ATen/native/xpu/BatchNorm.cpp:85-114. The operator registry maps
batch_norm/native_batch_norm to BatchNorm.cpp with oneDNN at
third_party/torch-xpu-ops/.opencode/skills/bug_scrub/prepare_data/pytorch_xpu_backend_analysis/xpu_supported_operators_complete_list.md:210-220,
while the SYCL implementation still has layout-dependent kernel selection in
BatchNormKernels.cpp:61-88. The reported B580 roofline gap (+0.0049 geomean R delta, 13 models)
points to inefficient backend/layout selection or memory bandwidth utilization for the batch_norm
transform on BMG rather than a correctness failure.

## Fix Approach

- Profile native_batch_norm on the listed B580 fp16 model shapes with oneDNN verbose and XPU kernel timing, separating oneDNN-backed paths from SYCL fallback/layout paths.
- Tune or route BMG fp16 channels-last/contiguous cases to the faster primitive, add shape-specific performance tests or benchmarks, and escalate primitive-level bandwidth/occupancy regressions to oneDNN if the bottleneck is inside the library call.
