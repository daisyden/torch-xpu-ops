## Root Cause

third_party/torch-xpu-ops/src/ATen/native/xpu/sycl/TensorTopKKernel.cpp:118 first tries the
optimized sbtopk path and falls back to segmented_group_select_pairs when it declines. For the
reported k=8, dim=64 case,
third_party/torch-xpu-ops/src/ATen/native/xpu/sycl/TensorTopKSbtopkKernel.cpp:106 routes large-batch
slices to subgroup topk; the CI-only wrong values point to that XPU topk selection path producing
incorrect ordering/values on PVC rather than Triton itself.

## Fix Approach

- - Reproduce on the failing PVC/driver, add CPU-vs-XPU topk regression tests for [1,1,8,8] k=2 and [8,64] k=8, then either fix the subgroup topk compare/index handling for float32 or gate the optimized sbtopk path off for the affected shapes/hardware until corrected.
