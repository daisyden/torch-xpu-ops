## Root Cause

The issue is a Dynamo/Inductor performance regression report: benchmarks/dynamo/common.py:1041-1164
measures eager versus torch._dynamo.run, and benchmarks/dynamo/common.py:2913-3035 warms eager and
optimized paths before collecting the Inductor timing. The affected workloads are benchmark-suite
entries such as pyhpc_turbulent_kinetic_energy, which is listed in
benchmarks/dynamo/common.py:144-154, plus HuggingFace models loaded by
benchmarks/dynamo/huggingface.py:50-66 and 139-155; the report states hardware, driver, Triton, OS,
and PyTorch are otherwise identical and only the oneAPI 2025.3.2 to 2026.0.0 runtime changed, so the
root is most likely a oneAPI compiler/runtime performance regression exposed through
Inductor-generated XPU kernels rather than a torch-xpu-ops operator implementation.

## Fix Approach

- - - Collect per-model Inductor generated code and profiler traces for the worst cases, especially pyhpc_turbulent_kinetic_energy float32 inference, comparing oneAPI 2025.3.2 versus 2026.0.0. - Route reduced kernels and timing deltas to the oneAPI compiler/runtime owners. - only add PyTorch/Inductor workarounds if a specific lowering pattern is identified as newly pathological under 2026.0.0.
