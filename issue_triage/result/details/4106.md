## Root Cause

test_errors_arange_xpu (inherited OpInfo error contract) does strict exception type/message checks
for arange invalid-input handling. Upstream range factories route this through shared bound/size
validation distinguishing TORCH_CHECK vs TORCH_CHECK_VALUE, while the XPU arange path diverges
(likely step casting/validation for out dtypes), so a semantically valid fractional-step input is
rejected as 'step must be nonzero' or with a mismatched error type. A backend semantic mismatch, not
wording-only.

## Fix Approach

- Align XPU arange argument validation and exception contract with upstream RangeUtils/RangeFactories for all (start,end,step,out) combos, especially fractional step with integral out: share/mirror upstream size computation and check ordering, avoid premature integer truncation of step in generic validation, and emit the same error class (ValueError vs RuntimeError) and regex-compatible message OpInfo expects.
- Add XPU regression for torch.arange(0,64,0.5,out=...) and adjacent boundary cases.
