## Root Cause

The failing workload is an Inductor torchbench cold-start performance run; torch-xpu-ops CI overlays
its benchmark lists into PyTorch before invoking the Inductor runner
(third_party/torch-xpu-ops/.github/actions/linux-e2etest/action.yml:40,
third_party/torch-xpu-ops/.github/actions/linux-e2etest/action.yml:44). The benchmark command uses
PyTorch's cold-start latency and AMP dtype controls (benchmarks/dynamo/common.py:3731,
benchmarks/dynamo/common.py:3758), and the issue reports a 0.8557 baseline/target latency ratio on
driver 26.19 versus 25.40, which is a roughly 16.9% slowdown. Because no operator/test source
changed in the repro and the only changed variable is the driver, this points to a driver/runtime
compilation or execution regression exposed by the moondream Inductor path rather than a
torch-xpu-ops kernel bug.

## Fix Approach

- Reproduce the moondream amp_fp16 inference command on 25.40 and 26.19 with identical PyTorch/torch-xpu-ops wheels, collect Inductor/Triton cache and driver profiling artifacts, then bisect driver components or file against the compute-runtime/IGC owner with the generated kernels and latency deltas.
- Keep the torch-xpu-ops issue open as a driver dependency and add a temporary dashboard annotation rather than changing operator code.
