## Root Cause

The FFT failures compare fake/meta strides against real XPU results for aten._fft_c2r.default, and
XPU registers _fft_c2r to _fft_c2r_xpu in yaml/native/native_functions.yaml lines 9376-9385. The
real XPU path calls native::xpu::_fft_c2r_mkl at src/ATen/native/xpu/SpectralOps.cpp lines 57-65,
whose oneMKL implementation performs c2c transforms, allocates a fresh output, clones input
contiguous, executes FFT, and returns that concrete layout at
src/ATen/native/xpu/mkl/SpectralOps.cpp lines 428-463; the generic meta implementation in
torch/_meta_registrations.py lines 611-622 models the MKL CPU path, not the XPU oneMKL layout, which
explains the reported stride mismatch (72,12,1) vs (12,60,1).

## Fix Approach

- - - Align XPU _fft_c2r output metadata with the concrete oneMKL result: either adjust the XPU oneMKL path to return the same contiguous/strided layout that meta_fft_c2r predicts, or add an XPU-aware meta/fake registration that matches native::xpu::_fft_c2r_mkl. - Add a focused fake crossref regression for hfft2/hfftn/irfft2/irfftn sample inputs and keep the max_unpool2d entries separate, since those already use explicit XPU max_unpool kernels in src/ATen/native/xpu/MaxUnpooling.cpp lines 27-42 and sycl/MaxUnpoolingKernels.cpp lines 81-215.
