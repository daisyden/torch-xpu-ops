## Root Cause

Failure in upstream DTensor math-op coverage (test/distributed/tensor/test_math_ops.py), where
floating-point comparisons use strict assertEqual checks and XPU distributed execution introduces
small numeric drift vs local tensors. Points to DTensor sharding/redistribution/reduction behavior
on XPU (especially reduce-style math ops), not a transport-layer collective crash. torch-xpu-ops
also tracks this upstream test in distributed skip lists, reinforcing a DTensor
correctness/integration issue.

## Fix Approach

- Reproduce the exact failing subtest/op on XPU, identify the first mismatching operator and placement pattern, compare local-vs-DTensor intermediate values before/after redistribute/reduction.
- In upstream DTensor, enforce numerically stable behavior for that op path (correct reduction semantics/accumulation dtype and placement propagation) and add a regression.
- only if it's a documented XPU kernel precision limitation should narrowly scoped XPU tolerances be added with justification.
