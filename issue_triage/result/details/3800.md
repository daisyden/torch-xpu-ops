## Root Cause

This is a logspace XPU numerical accuracy issue in the tensor-creation path. The XPU wrapper
dispatches logspace to the SYCL kernel at
third_party/torch-xpu-ops/src/ATen/native/xpu/RangeFactories.cpp:147, and the floating branch
computes scalar_base, scalar_start/scalar_end, and step in scalar_t at
third_party/torch-xpu-ops/src/ATen/native/xpu/sycl/RangeFactoriesKernel.cpp:311 through
third_party/torch-xpu-ops/src/ATen/native/xpu/sycl/RangeFactoriesKernel.cpp:320. The CPU
implementation deliberately uses double for scalar_base and step at
aten/src/ATen/native/RangeFactories.cpp:128 through aten/src/ATen/native/RangeFactories.cpp:140,
while the XPU test expects close/exact logspace values in
third_party/torch-xpu-ops/test/xpu/test_tensor_creation_ops_xpu.py:3872 through
third_party/torch-xpu-ops/test/xpu/test_tensor_creation_ops_xpu.py:3888.

## Fix Approach

- Update RangeFactoriesKernel.cpp so floating logspace computes the base exponentiation and step in a higher-precision accumulator matching the CPU/CUDA algorithm, then cast to the output dtype at store time.
- Add a focused XPU regression covering float32 base=2 and the reported Windows Arc B580 tolerance-sensitive case.
