## Root Cause

The reported behavior comes from an explicit test-side guard in upstream flex-attention accuracy
checking: `_gold_check` skips when fp32 compiled output error exceeds eager error
(`test/inductor/test_flex_attention.py:8394-8413`). The skip condition is dtype-based (`eager.dtype
== torch.float32`) and not XPU-specific, while XPU enablement is only from generic device-type
instantiation (`...:9518-9520`). This indicates a known compiled-vs-eager fp32 accuracy limitation
in upstream compiled FlexAttention validation logic, not a torch-xpu-ops-only kernel registration
gap.

## Fix Approach

- Track this as an upstream compiler/attention numerics item: collect per-backend error distributions for the same LearnableBiases parameterizations and identify which compiled decomposition contributes most to fp32 drift.
- Then tighten/fix the underlying compiled path or adjust tolerance policy with explicit backend rationale, and remove the skip once parity criteria are met.
