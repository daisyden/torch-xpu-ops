## Root Cause

The XPU backend does not register/implement aten::sspaddmm or aten::sspaddmm.out, so sparse-sparse
addmm has no XPU path. Upstream has CPU-side sparse logic; accelerator paths are generally NYI (CUDA
explicitly NYI), so this is a backend implementation gap, not a regression. As a sparse operator, it
belongs to Sparse taxonomy, not generic GEMM.

## Fix Approach

- Add XPU dispatch registration for sspaddmm and sspaddmm.out in torch-xpu-ops, then implement a new XPU/SYCL sparse kernel matching CPU semantics (layout/shape checks, alpha/beta handling, out-tensor behavior).
- Reuse CPU validation/error messages for consistency.
- add XPU sparse tests covering functional + out variants, dtype/device coverage, and expected error cases.
