## Root Cause

Inductor/Triton launcher-runtime compatibility bug, not a per-UT bug. XPU static launch is in
torch/_inductor/runtime/static_triton_launcher.py (StaticallyLaunchedXpuKernel); there is no
XPULauncher class there, so XPULauncher comes from the Triton XPU backend path. The signature
'XPULauncher' object has no attribute 'mod' points to a lifecycle mismatch where code assumes a
module-handle field (mod) exists on Windows XPU launcher objects but it is not initialized, causing
widespread launch-time crashes across many UTs.

## Fix Approach

- Patch the Triton XPU launcher to make launcher state layout consistent across platforms: ensure the module-handle attribute expected by cleanup/launch paths is always initialized (or remove all mod accesses in favor of one canonical field).
- Add a defensive getattr(..., None) guard in destructor/close paths to avoid hard AttributeError on partially initialized launchers.
- Add a Windows XPU regression that constructs/tears down the launcher through the Inductor static-launch flow.
