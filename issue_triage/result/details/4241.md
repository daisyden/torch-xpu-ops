## Root Cause

FSDP with sync_module_states triggers distributed collectives through ProcessGroupXCCL, and the
failing path reported in the issue is a oneCCL Level Zero call during collective execution
(ZE_RESULT_ERROR_UNKNOWN). The XPU backend routes broadcast/reduce_scatter through ProcessGroupXCCL
into oneCCL wrappers (`third_party/torch-xpu-ops/src/xccl/ProcessGroupXCCL.cpp:1436-1483`,
`1780-1825`) which call oneCCL collectives (`third_party/torch-xpu-ops/src/xccl/xccl.cpp:105-133`,
`136-169`). FSDP state sync and sharded training depend on these collectives via
`_sync_module_params_and_buffers` and `_broadcast_coalesced`
(`torch/distributed/fsdp/_init_utils.py:1110-1167`, `torch/distributed/utils.py:318-328`), so the
crash is consistent with an XCCL/oneCCL communication-layer failure rather than model logic.

## Fix Approach

- Add a targeted XCCL regression reproducer for FSDP init+first-backward on 2 ranks, then instrument ProcessGroupXCCL collective entry/exit and oneCCL return codes around broadcast and reduce_scatter to capture whether failure is at init-broadcast or first gradient collective.
- In parallel, test and document a safe default/fallback for problematic IPC-handle exchange modes (e.g., sockets fallback when pidfd path fails) in the XCCL/oneCCL initialization path, and gate it by topology/virtualization detection if needed.
