## Root Cause

The regressions are concentrated in BatchNorm running statistics keys (e.g.,
running_mean/running_var) under torch.compile+inductor training, which points to compiled-training
state update drift rather than a pure inference mismatch. In XPU BatchNorm, running stats are
updated with momentum and unbiased variance in the kernel path
(`third_party/torch-xpu-ops/src/ATen/native/xpu/sycl/BatchNormKernels.cpp:5111-5118`), and the
dispatch wrapper forwards directly into that kernel
(`third_party/torch-xpu-ops/src/ATen/native/xpu/BatchNorm.cpp:101-113`), so operator-side logic
follows expected semantics. Given failures are weekly-vs-release and observed in inductor benchmark
runs, the likely regression surface is upstream compile/AOT/graph handling of mutable BN buffers
rather than a missing XPU op implementation.

## Fix Approach

- Bisect between the cited good/bad PyTorch commits using the timm repros, then instrument compiled vs eager BN buffer updates (running_mean/running_var) per step to find the first divergence.
- Add an inductor regression test that asserts parity of BN running stats after several training iterations on XPU for affected model patterns, and patch the upstream compile path that mishandles BN state mutation/aliasing.
