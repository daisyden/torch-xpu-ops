## Root Cause

The slowdown is consistent with the XPU FP8 per_block path going through oneDNN scaled_mm blockwise
recipes that are less optimized on BMG than tensorwise/rowwise. In PyTorch's XPU scaled-BLAS code,
blockwise modes do extra scale layout normalization (transpose/contiguous) before dispatch, adding
significant overhead in decode-heavy workloads; the code also documents current oneDNN limitations
for group-scale FP8 on BMG, so the backend path is constrained vs per_row/per_tensor kernels.

## Fix Approach

- Treat as a oneDNN-backed scaled_mm perf gap: capture oneDNN verbose/prof traces for per_row vs per_block on the reported shape, optimize/eliminate per-call scale transpose+contiguous in the per_block path (cache/prepack scales in an oneDNN-friendly layout), add a BMG-specific fast path or heuristic fallback to rowwise when blockwise selection is slower.
- Coordinate with oneDNN to improve blockwise FP8 GEMM on BMG.
- add a TorchAO regression benchmark gate for per_block latency.
