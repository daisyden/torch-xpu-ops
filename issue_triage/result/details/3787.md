## Root Cause

The failing functorch vmap tests explicitly exercise scaled_dot_product_attention under each
platform-specific backend and call F.scaled_dot_product_attention inside vmap
(third_party/torch-xpu-ops/test/xpu/functorch/test_vmap_xpu.py:3888,
third_party/torch-xpu-ops/test/xpu/functorch/test_vmap_xpu.py:3967). The XPU test file appends
CUDNN_ATTENTION even though it is unsupported on XPU
(third_party/torch-xpu-ops/test/xpu/functorch/test_vmap_xpu.py:108,
third_party/torch-xpu-ops/test/xpu/functorch/test_vmap_xpu.py:110), while the XPU SDPA selector in
PyTorch only accepts overrideable, flash, math, or memory-efficient backends and raises "No
available kernel" after rejecting the requested backends
(aten/src/ATen/native/mkldnn/xpu/Attention.cpp:180,
aten/src/ATen/native/mkldnn/xpu/Attention.cpp:249). The overrideable XPU SDPA path is backed by
oneDNN/mkldnn code, so this is a backend-selection/test-porting gap around unsupported SDPA backend
combinations rather than a missing generic vmap kernel.

## Fix Approach

- Remove CUDNN_ATTENTION from the XPU SDPA backend parameterization or xfail only that unsupported backend, then add coverage that XPU vmap SDPA still runs for math/flash/overrideable supported paths.
- If oneDNN overrideable is selected but rejects valid XPU inputs, reduce that case separately and fix the mkldnn/xpu attention constraints.
